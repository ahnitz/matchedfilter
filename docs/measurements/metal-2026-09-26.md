# Metal execution on Apple M2

Measured on Apple M2, 24 GiB unified memory, macOS 26.5.2, Python 3.13.
The baseline is `b3a1af0`. Both builds use the same FP32 Slang algorithms;
no coarse gate, precision, normalization, or public API changed.

## Changes

- Use the shared `SINGLE_BIN` specialization for flat peaks and hierarchical
  refinement at 2048, 4096, and 8192 points. Multi-bin calls retain the general
  kernel. Staging is 16, 32, and 32 KiB respectively.
- Submit distinct flat block windows in one Metal command buffer per bounded
  batch. Buffer offsets select each group's spectra and output rows; there is
  no extra output scatter. The existing shared series scheduler handles this
  for both Vulkan and Metal.
- Cache Objective-C selectors and typed message-call wrappers per context.
- Record GPU duration for full-output command buffers as well as peak calls.

## Warm public calls

Each spectral batch has 128 data spectra and 512 normalized random complex
templates. Inputs are unchanged across repeated calls. Full windows, one bin,
threshold 5.5; hierarchical filtering uses explicit band 256 and coarse
threshold 4. Setup and compilation are excluded. Values are median wall-clock
milliseconds from nine calls after two warmups, including host dispatch and
peak readback. Before/after suites ran separately on the same machine.
An additional seven-round interleaved kernel comparison confirmed the flat
specialization gains.

| FFT length | Flat before | Flat after | Hierarchical before | Hierarchical after |
|---:|---:|---:|---:|---:|
| 2048 | 25.16 | 19.10 | 5.03 | 4.56 |
| 4096 | 37.27 | 28.98 | 6.00 | 5.26 |
| 8192 | 132.55 | 111.22 | 13.92 | 12.26 |

Flat elapsed time falls 16–24%; hierarchical time falls 9–12%. The fraction
of refined pairs is unchanged at each size: 8.13%, 8.07%, and 8.35%.
These explicit-gate workloads measure execution cost, not calibration quality.

Automatic `run_series()` with 43 blocks and 128 templates improves from
2.55 to 2.04 ms at 2048, 3.59 to 2.72 ms at 4096, and 11.74 to 9.91 ms at
8192. Explicit-block calls have similar times, so automatic block selection
adds little overhead here.

At 4096 points, 128 blocks and 32 templates, varying the number of distinct
windows gives:

| Window groups | Before, ms | After, ms |
|---:|---:|---:|
| 1 | 2.95 | 2.25 |
| 2 | 3.36 | 2.30 |
| 16 | 7.35 | 2.52 |
| 128 | 41.12 | 4.16 |

The 128-group case is 9.9× faster. The uniform-window improvement comes from
the kernel and host-call changes; grouping accounts for the much larger gain
with distinct windows. Reproduce the submission comparison with
`python tools/audit_class_execution.py --device gpu --suite submissions --rounds 7 --json .local/submissions.json`
(create `.local/` first).

## Independent Metal FFT comparison

MLX 0.32.2 provides a second GPU implementation. Inputs reside on the device;
matchedfilter full output uses a preallocated `empty_shared(..., readback=True)`
array, and MLX output stays on the device. Timings include synchronization but
exclude conversion to NumPy. MLX evaluates
`mx.fft.ifft(data[:, None, :] * mx.conj(templates[None, :, :]), norm='forward')`.
Its peak path additionally evaluates absolute value, argmax and complex-value
gather. The normalization matches matchedfilter's unnormalized inverse.

The following are nine-round alternating medians for 16 data spectra × 128
templates, full window, threshold zero. Plans and inputs are cached; MLX
allocates its expression results while matchedfilter reuses its output.

| Length | matchedfilter full, ms | MLX product + IFFT, ms | matchedfilter peaks, ms | MLX product + IFFT + peaks, ms |
|---:|---:|---:|---:|---:|
| 2048 | 0.858 | 2.315 | 0.941 | 4.684 |
| 4096 | 1.515 | 4.294 | 1.159 | 9.197 |
| 8192 | 5.032 | 10.993 | 3.845 | 18.694 |

Also checked 8×64 batches. All tested peak indices match MLX, and maximum
full-output error divided by the reference maximum is below 2.6e-6.
The full-output advantage is 2.2–2.8× for the table's workloads; this measures
complete library calls, including allocation-policy differences, rather than
isolated FFT arithmetic. MLX's [IFFT documentation](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.fft.ifft.html)
defines the normalization used here.

## Remaining limits and rejected choices

At 8192 points the optimized large flat call spends 110.81 of 111.22 ms on
the GPU. More host-side submission work will have little effect on that
uniform batch. Smaller batches have a larger host/synchronization fraction;
the 8×64 flat call spends about 0.87 of 1.18 ms on the device.

Smaller exchange staging was slower in paired trials. Experimental 32- and
64-point-per-thread decompositions at 8192 were also slower than the retained
16-point layout: roughly 458 and 655 ms versus 113 ms for 128×512 at threshold
zero. Those experimental kernels are not shipped. Changing the FFT arithmetic
also produced a handful of near-tied argmax differences, independently checked
against double-precision transforms.

These results establish an improvement over the previous backend and an
advantage over this MLX reference. They do not establish a hardware throughput
bound or near-optimality across Apple GPU generations. The remaining priority
is the 8192-point exchange/occupancy cost; a different multi-dispatch FFT would
need to beat the fused path after accounting for intermediate memory traffic.
The wider supported size range retains its existing kernels.

## Validation

The physical M2 run passed 970 correctness/API tests; the sole initial failure
required Git metadata missing from the isolated source archive. After restoring
the actual baseline revision metadata, that test passed too (971 unique tests
passed). The 73 skips covered Vulkan-only checks, opt-in timing checks, and
unavailable development tools. No Metal size was skipped as unsupported.
All 28 opt-in performance checks passed, including the new single-bin/general
comparisons at 2048–8192 points and the grouped-submission gate. A second run
against the saved machine/runtime baseline also passed all 28 checks.

Tests compare flat and hierarchical specialized kernels against the general
kernel while changing windows, thresholds, and bin counts on reused plans.
Existing grouped-window tests now exercise Metal, including template changes,
cache eviction, padded input, output ordering, and submission count. Six
selected Metal sources reproduce byte-for-byte across build directories.
